# IOLITE detailed release notes

## v1.28.0 — the hardened-target simulation lab (internal readiness dry-run)
**Goal:** before any real engagement, prove the tool works end-to-end behind the hardest defences —
and see exactly how it builds authorization intent, where operational problems appear, what it
confirms, and what the report says. `iolite/intent/simlab.py` is a fully synthetic, deterministic
lab that drives the **unmodified** engine against models of Google / Microsoft / Cloudflare /
Akamai-class stacks. Nothing touches a real network; every response is fabricated by a
`HardenedTarget` (it is a validation harness for the operator's own authorised-testing tool, not an
exploit). Run it: `iolite sim [--out report.md]` or `python -m iolite.intent.simlab`.

What the lab exercises (the real code paths):
- **Defence models:** token-bucket rate-limiting (429 + Retry-After), edge WAF/bot walls (vendor
  headers + block pages), JS/captcha challenges, and short-lived-token expiry (401) — on a shared
  **virtual clock** so pacing and rate-limiting interact for real.
- **Intent building** via `LiveSession.ingest_raw`: ownership read from `owner_id`↔JWT `sub`,
  boundaries learned by **contrast** (owner ALLOW vs non-owner clean-deny), confidence growing per
  observation. A WAF/429/challenge is classified as a **defence**, so it never teaches a boundary.
- **Confirmation** via the real `confirm.confirm_leads` → `executor`/`pacer` + the value-presence
  oracle: findings only on a clean 2xx, with EV ordering, AIMD backoff, soft-penalty+park on a WAF,
  and bounded retries.
- **Execution stress** via `executor.run_tasks` with `refresh_auth`: short-lived tokens expire under
  load and are transparently refreshed; the run never stalls.
- **The dossier** via `dossier.render`, plus a per-profile operational diagnosis.

Result (seed 7): **READY — 4/4** profiles operational; the seeded BOLA **and** cross-tenant exposure
surfaced and value-presence-confirmed on every profile; **zero** false boundaries from a defence and
**every** finding from a clean 2xx; rate-limit backoff honoured `Retry-After`; auth-expiry
auto-refreshed. Honest operational notes included (edge may park a probe → re-visit; Azure/Front-Door
not yet vendor-fingerprinted — caught by body phrase regardless). New tests:
`tests/test_simlab.py` (7). Suite: **337 passed, 1 env-only skip**. Docs: `docs/notes/WALL17.md`; the full
readiness report is generated by the command above.

## v1.21.0 — PARALLEL execution + the wired live confirmer (generate → execute → dispose)
**Goal:** finish the loop asked for — wire the defense-aware executor into the live confirmer
and add real parallelism — so IOLITE confirms the EV-ranked leads at top speed on a hardened
target. Additive; pre-existing engine byte-identical; suite **313 → 320**.

- **`executor.run_tasks_concurrent` — real parallelism.** A thread pool (size = pacer.concurrency)
  parallelizes request LATENCY — the real bottleneck on a remote target — while the pacer, held
  under a lock, keeps the GLOBAL rate within the learned safe envelope. Same defence handling,
  budget, EV ordering, auth-refresh, scope guard, and clean termination as the sequential path.
  Measured ~5.6× faster than sequential in the latency-bound regime (6 workers, 20 ms/req), while
  still backing off and parking WAF walls.
- **`confirm.py` — the wired live confirmer.** Turns the EV-ranked READ-side leads
  (read_bola / chained / tenant) into safe cross-principal GET replays: replay the holder's own
  request as the attacker principal, execute through the defense-aware (parallel, paced) executor,
  and DISPOSE by VALUE PRESENCE — a finding requires the attacker's response to reproduce the
  holder's object-specific private value on a CLEAN 2xx. A clean 403 is a (correct) non-finding;
  a WAF/challenge is parked, never a finding. Writes are never replayed here (that is the
  reversible intervention saga, Wall-7). Ships a scope-guarded, read-only `http_sender` for real
  use; tests inject a simulated target.
- **`iolite hunt --replay`.** The gated, defense-aware replay confirmation of the leads, behind an
  attested engagement, scope-guarded, own-accounts-only (`--principals-file` supplies your own
  accounts' auth headers; `--base-url` prefixes the lead paths). Seeds the pacer and reports the
  learned defence profile. The dossier gains a "Live-confirmed (replay)" section.

This closes the chain end to end: GENERATE (divergence, scanner-blind families) → SCHEDULE (EV) →
EXECUTE (parallel + AIMD-paced + defence-aware) → DISPOSE (value-presence) → DOSSIER. Proven on a
simulated defended+vulnerable target: of three leads, only the truly exposed object was confirmed,
the properly-protected one was a clean non-finding, and the WAF-walled one was parked — with
adaptive pacing and parallel execution throughout. Tests: `test_confirm.py`, `test_executor.py`
(+concurrency). Docs: `docs/notes/WALL11.md`.

Honest floor: replay confirms READ-side exposure only; writes/fields/state still go through the
reversible intervention (Wall-7). Parallelism helps only up to the target's safe rate — the pacer
remains the global ceiling. Own accounts only; attested RoE; scope-guarded; read-only sender.

## v1.20.0 — DEFENSE-AWARE execution: learn the target's defences, ride the ceiling
**Goal:** the strongest programs sit behind WAFs, bot-management and rate limiters. v1.19 was
blind to all of it — it would hammer into a block, and (worse) mistake a WAF/bot 403 for an
authorization boundary, corrupting the intent model. v1.20 senses defences, learns them, and
executes at the fastest pace the target tolerates. Additive; pre-existing engine byte-identical;
suite **294 → 313**.

- **`defense.py` — tell a real denial from a defensive block.** Classifies every response:
  `RATE_LIMITED` (429 / Retry-After), `WAF_BLOCK` (vendor fingerprint — Cloudflare / Akamai /
  Imperva / AWS WAF / Sucuri / F5 / DataDome / PerimeterX / ModSecurity), `CHALLENGE` (captcha /
  JS interstitial), `AUTH_EXPIRED` (token/session expiry) vs a clean `FORBIDDEN_AUTHZ`. A
  structured JSON `{"error":"forbidden"}` is correctly a real authz denial; an HTML "Attention
  Required" with a `cf-ray` header is a WAF block. A per-host `DefenseProfile` is learned online
  (safe rate, latency baseline, vendor, block counts) and seeds the pacer.
- **Precision fix for hardened targets.** `policy_learn` now counts a non-owner denial as an
  enforced-boundary signal ONLY when it is a clean authz denial — a WAF/bot/challenge/expiry
  response never teaches a false boundary. This is the key correctness gain on big targets.
- **`pacer.py` — AIMD adaptive rate control.** TCP-style additive-increase / multiplicative-
  decrease: nudges the rate up on every clean success, halves it (and shrinks concurrency) on a
  pace block, honors Retry-After, and distinguishes a global pace block (429/5xx → full back-off)
  from a request-specific WAF wall (light touch, don't tank throughput). It discovers and rides
  just under the target's ceiling — maximum safe speed.
- **`executor.py` — defense-aware, EV-prioritized task runner.** Runs the gated live probes
  highest-EV-first under the pacer + a hard budget, backs off and bounded-retries on blocks,
  parks a WAF-walled path instead of hammering it, refreshes auth on token expiry, and enforces
  scope per request. Hands back responses + the learned defence profile; never decides a finding.
- **Live integration.** `live_session` now emits `defense` events (rate-limit / WAF / challenge /
  auth-expiry) as you browse and builds the `DefenseProfile`, so by the time you run the gated
  step IOLITE already knows the target's safe rate and vendor. The live hook forwards the headers
  needed to fingerprint the edge.

Proven against a simulated hardened target (5 req/s ceiling + Cloudflare WAF path + token
expiry): the executor completed every legitimate task, discovered and rode just under the rate
ceiling (start 12 → settle ~3.3 req/s, halving the wall-clock vs a naive run), parked the WAF
path after one retry, refreshed the expired token and recovered, and learned the vendor + safe
rate — all deterministically. Tests: `test_defense.py`, `test_pacer.py`, `test_executor.py`.
Docs: `docs/notes/WALL10.md`.

Honest floor: the pacer finds a *sustainable* rate, not a magic bypass — a hard bot wall (full
JS/captcha) is parked, not defeated (IOLITE never solves captchas or forges humanity). Defence
learning sharpens with observations. Still own-accounts-only, scope-guarded, attested-RoE for
any live step.

## v1.19.0 — DEEP response reading + a CONTRAST-learned intent model
**Goal:** the self-critique of v1.18 was that the live reader was shallow (a couple of flat
scalars) and the intent builder ignored the single most reliable signal — the contrast
between what one account is ALLOWED and another is DENIED. v1.19 reads the whole response and
learns the policy from that contrast. Additive; pre-existing engine byte-identical; suite
**280 → 294**.

- **`observation.py` — deep extraction, one fact per call.** Parses the FULL response:
  nested objects and COLLECTIONS (a list endpoint reveals the ids a principal can enumerate),
  the server-stated `owner_id` / `parent_id` / `tenant_id` / `state` (Zanzibar tuples), typed
  fields (id / secret / enum / timestamp / content), a few safe response headers, and the
  ENFORCEMENT class of the status (ALLOW / AUTHZ-DENY 403 / AUTHN-DENY 401 / MASKED 404 /
  RATE 429). It also decodes the acting principal's JWT CLAIMS (sub / role / tenant) from its
  own Authorization header — claims only, never the token — so identity is read, not guessed.
- **`policy_learn.py` — learn the access-control function by CONTRAST.** Ownership is read
  from `owner_id == sub`, not a heuristic. A boundary is LEARNED when an owner is allowed AND
  a non-owner is denied on the same type → an *enforced* owner-scoped intent with a confidence
  that grows per observation. A VIOLATION is the opposite contrast (a non-owner reproduced the
  owner's private value), now pinned to the real owner. It also learns tenant isolation and
  surfaces ENUMERATION exposure (a list that returns other principals' ids).
- **Live integration + new signals.** `live_session` now feeds every call through
  `observe → PolicyLearner` and emits, in real time: `corroborated` (precise BOLA / tenant),
  `boundary_learned` (the intent model announcing a confirmed, enforced boundary),
  `enforcement_denial` (a denial that teaches the boundary), and `enumeration_leak`
  (chained-BOLA precursor). `snapshot()` / the dossier now carry the LEARNED policy table
  (intent · enforced? · confidence · evidence counts) per object type.
- **Hook upgrade.** `iolite_live_hook.js` forwards response bodies + safe headers and decodes
  JWT claims in the browser (sends claims, never the token). `iolite watch` prints the learned
  enforced boundaries on stop.

Proven live end-to-end: alice owns vault 1001; bob reading it fires a PRECISE BOLA (via
`owner_id`), carol's 403 fires `enforcement_denial` + `boundary_learned` (vault = owner-scoped,
enforced), and bob's list fires `enumeration_leak` — all from browsing, 0 crafted requests.
Tests: `test_observation.py`, `test_policy_learn.py`, plus live/collector integration. Docs:
`docs/notes/WALL9.md`.

Honest floor: the contrast learner needs the denial to be observed — i.e. you must actually
try another account's object (and get the 403) for the boundary to be *learned enforced*; a
boundary never contrasted stays "owner_scoped / unenforced-unknown". Still passive, scoped,
own-accounts-only.

## v1.18.0 — SCAN WHILE YOU BROWSE: live, passive, instant (`iolite watch`)
**Goal:** stop the capture-then-analyse round-trip. Build the authorization-intent model and
confirm cross-account exposure AS you use the target with your own accounts — faster
(incremental), more accurate (real responses), and still passive (the tool crafts nothing).
Additive; pre-existing engine byte-identical; official suite **270 → 280**.

- **`live_session.py` — the incremental brain.** Ingests request/response pairs one at a
  time behind online indexes (`value→objects`, `object/principal→values`), so each event is
  O(fields) — no recompute while you click. HOT PATH: the instant one of your accounts loads
  an object another of your accounts owns and reproduces its discriminating private value, a
  BOLA (or cross-tenant) is CONFIRMED and surfaced immediately — zero crafted requests. The
  value-presence Δstate proof is the same one ONYX uses, now computed live from what your
  own browser received. `snapshot()` runs the full Wall-5/6 methodology (learn → corroborate
  → lattice → EV-ranked divergence) on everything seen so far.
- **`collector.py` — a loopback-only receiver.** A tiny stdlib server bound to 127.0.0.1 that
  serves the hook, receives one POST per call, feeds the session, and streams confirmations
  back. Enforces scope; binds only to localhost; sends nothing outward.
- **`assets/iolite_live_hook.js` — the passive live hook.** Wraps the page's own `fetch`/XHR
  to record request + response BODIES and forward each to your local collector. It observes
  only what your client already sends/receives for legitimate use; its only added destination
  is your loopback collector; it never recurses into itself.
- **CLI `iolite watch --scope <hosts> [--roe e.json] [--principals A,B]`.** Starts the
  collector, prints a one-line snippet to paste in EACH account's DevTools console, then
  prints live confirmations as you browse; on Ctrl-C it writes the dossier. One command to
  scan during use.

Faster: incremental, indexed — instant alerts, no mid-session recompute. More accurate: real
